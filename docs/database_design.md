# CarbonTrace Database Design

## Conventions

- PostgreSQL; SQLAlchemy 2.0 models and Alembic migrations.
- UUID primary key `id` for entities. UUID values are generated by the application or database.
- UTC `created_at` and `updated_at` timestamps on mutable entities. Append-only execution and audit records require `created_at`; `updated_at` may be omitted where a record is immutable.
- `organization_id` is non-null on tenant-owned records and is included in tenant-scoped indexes and foreign-key designs.
- JSONB is reserved for source payloads, structured agent results and extensible metadata; queryable business attributes remain typed columns.
- Store emissions in `kg_co2e` as high-precision numeric values. Convert for display, not during accumulation.
- Use restrictive foreign-key deletion for accounting, execution and report provenance. Prefer explicit archival/soft deactivation to cascading deletion of audit history.

## Entity relationship overview

```text
users --< organization_members >-- organizations
organizations --< data_sources --< ingestion_runs --< activity_records
organizations --< pipeline_runs --< agent_runs
organizations --< activity_records --< calculation_results >-- emission_factors
organizations --< anomaly_records
organizations --< sustainability_insights
organizations --< reports
organizations --< audit_logs
```

`emission_factors` can be shared (`organization_id IS NULL`) or owned by one organization. All other listed business data is organization-scoped.

## Referential integrity and tenant isolation

Where two tenant-owned rows are related, include `organization_id` in the relationship guard. A practical PostgreSQL pattern is a unique constraint on `(organization_id, id)` for parent rows and a composite foreign key `(organization_id, parent_id)` from the child. This prevents accidental cross-organization links even if application code has a bug. For a shared-or-tenant factor, validate factor ownership explicitly: factor organization is null or equals the result organization.

All API queries must include the authenticated organization membership scope. A guessed UUID is not authorization. Membership, object access and role checks are verified for every request. Database row-level security may be considered later, but it does not replace explicit application authorization.

## Initial indexes and constraints

- Add indexes for all foreign keys used in joins and deletes.
- Add check constraints for enumerated statuses/scopes, positive or non-negative quantities where the domain permits, valid date ranges, non-negative counts and percentage/confidence bounds.
- Use uniqueness constraints for email, membership, source idempotency, activity fingerprint and calculation idempotency.
- Avoid broad JSONB indexes until actual query patterns justify them.
- Add indexes for tenant+time analytics queries and paginate large list endpoints.

## Migration and retention notes

Create schema changes only through Alembic. Initial migration should create PostgreSQL enum/check strategy consistently (prefer VARCHAR plus check constraints for easier forward migrations), UUID support, tables, composite keys, constraints and indexes. Store uploads and PDFs outside public static directories; define a retention policy before production deployment. Audit and calculation provenance should not be silently deleted when source files are removed.
